# Deployment (Ubuntu 24.04, Docker, Nginx, Cloudflare)

1. **Server:** `apt update && apt upgrade`, enable `unattended-upgrades`, create a non-root `deploy` user, SSH keys only (`PasswordAuthentication no`), `fail2ban`.
2. **Firewall (UFW):** default deny incoming; allow SSH from your IP; allow 80/443 **only from Cloudflare ranges**. Never open 27017 or 6379.
3. **MongoDB:** use a managed cluster or a private host with auth + TLS and a least-privilege user. Put the same URI in `.env.production` for both API and worker. For Atlas, allow only the server's fixed public egress IP (`/32`); never use `0.0.0.0/0`.
4. **Env:** production values for every secret; `NODE_ENV=production`, `CORS_ORIGINS=https://voxzin.com`, `SITE_URL`, `API_URL=http://api:4000/v1`. Configure either `SMTP_URL` or `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, and `SMTP_FROM` to send email. Keep SMTP credentials out of Git. For the zero-cost Cloudflare forwarding + Brevo Free newsletter setup, sender DNS, SMTP values, daily cap, and testing steps, see [NEWSLETTER.md](./NEWSLETTER.md).
5. **TLS and reverse proxy:** the host Nginx owns public ports 80/443 and proxies VoxZin to `http://127.0.0.1:13006`. Configure TLS on host Nginx (for example, with Certbot) and set Cloudflare SSL/TLS to **Full (strict)**. The production Compose stack does not run a second Nginx or publish public ports.
6. **Cloudflare:** managed WAF rules, bot fight mode, rate limiting on `/api/v1/auth/*`, Always HTTPS, proxy DNS records.
7. **Build and push** images with Jenkins (see `Jenkinsfile`) or locally: `docker build -f infrastructure/docker/Dockerfile --target web --build-arg NEXT_PUBLIC_SITE_URL=https://voxzin.com -t voxzin-web .` (also `api`, `worker`). `API_URL` is baked into the web build.
8. **Run:** `IMAGE_TAG=<tag> infrastructure/scripts/deploy.sh` (health-checks API, web, and the worker before marking a release successful). The worker is ready only when MongoDB, Redis, and its newsletter SMTP configuration are available. Redis waits for its health check before the worker starts; its limited capabilities let the official Redis entrypoint correct ownership on its persistent AOF directory without exposing the volume. If deployment fails, API and web are rolled back; inspect worker and Redis logs before retrying. The API image prepares `/data/uploads` for its non-root user, and the one-shot `uploads-init` service fixes ownership on the persistent uploads volume before the API starts. This preserves existing image files. First time: run `pnpm db:seed` and `pnpm create-admin` against the production database from a trusted machine.
   Admins can invite team members from **Admin → Users**. The email link expires after 24 hours; invitees create their own password and must set up two-step verification at first sign-in. The main admin sign-in can be managed from the env file: set `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_ROLE` (`super_admin` or `admin`) and `ADMIN_PASSWORD` (at least 12 characters) in `.env.production`. On start the API creates or updates that account (name and role always follow the env). The env password is applied only when it is new or you change it, which also signs that user out of other sessions; existing MFA is kept. A password set through **Forgot password?** is therefore not undone by a restart. Keep the file readable only by the deploy user (`chmod 600`), and remove `ADMIN_PASSWORD` from it to stop managing the account this way.

   **Password reset:** the admin sign-in page has a **Forgot password?** link. It emails a one-time link (valid 30 minutes, stored only as a hash, one email per minute per account) to the account's address; the reply never reveals whether an address is registered. It needs working SMTP settings (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`; for Gmail use an app password) and `SITE_URL` set to the public address. After a reset every other session is signed out; two-step verification still applies at sign-in.
9. **Backups:** schedule `infrastructure/scripts/backup-mongo.sh` (cron), then test a restore (BACKUP-RESTORE.md).
10. **Monitoring:** not wired in code yet. Add Sentry DSN, OpenTelemetry exporter and uptime checks, and alert on container restarts and repeated `auth.login_failed` audit events.

11. **Search and AI visibility (SEO):** the code already publishes what search engines and AI assistants need: `robots.txt` (allows Google, Bing, Apple, ChatGPT/OpenAI, Perplexity, Claude and other crawlers; only `/admin`, the raw API and internal search are closed), `/sitemap.xml`, a Google News sitemap at `/news-sitemap.xml` (articles from the last 48 hours), `/feed.xml` (RSS), `/llms.txt` (a plain-language map of the site for AI tools), `NewsArticle` structured data with sources, canonical links, and Open Graph/Twitter cards. Nobody can force a search engine or an AI assistant to show a site, so these steps get VoxZin found; ranking then depends on regular, original, well-sourced articles.

    - **Instant indexing (IndexNow):** add `INDEXNOW_KEY=<32 hex characters>` to `.env.production` (create one with `openssl rand -hex 16`) and redeploy. After that, every time an article is published (by hand or by the scheduler), edited or deleted, Bing, Yandex and other participating engines are told right away. Bing's index also feeds ChatGPT search and Copilot. The site serves the key at `https://voxzin.com/<key>.txt`; open that address to check it shows the key. If the key is missing nothing breaks, you just lose the instant ping.
    - **Google Search Console (manual, free):** add `https://voxzin.com` as a property (the DNS TXT method works best with Cloudflare), then submit `https://voxzin.com/sitemap.xml` and `https://voxzin.com/news-sitemap.xml`. Google no longer accepts pings, so the sitemaps and this tool are how Google learns about new articles.
    - **Bing Webmaster Tools (manual, free):** sign in, import the site from Google Search Console, and submit the same two sitemaps.
    - **Google News (manual):** apply at publishercenter.google.com once there are enough original articles; the news sitemap is already in place.
    - **Social profiles:** fill in the links under **Admin → Settings → Social**. They are added to the site's structured data so search engines connect the VoxZin site with its X, Facebook, YouTube and LinkedIn pages.
    - **Check it works:** `https://voxzin.com/robots.txt`, `/llms.txt`, `/news-sitemap.xml`, and Google's Rich Results Test on any article address.
